Goal:

Implement the first minimally working C raft core state machine on top of the C log subsystem from Phase 6.

This phase should make the C RawNode path capable of basic Raft behavior:

* initialize a C raft node from `raft_config_t`,
* load HardState and ConfState from `raft_storage_ops_t.InitialState`,
* initialize the C log from Storage,
* tick election and heartbeat timers,
* campaign and become candidate/leader,
* request votes and count votes for simple voter configurations,
* append no-op entry on leadership,
* accept client proposals on leader,
* reject/drop proposals appropriately on non-leader according to current skeleton policy,
* send basic `MsgApp`, `MsgAppResp`, `MsgHeartbeat`, `MsgHeartbeatResp`, `MsgVote`, `MsgVoteResp`, and local `MsgHup` handling,
* produce Ready data through existing C RawNode ready path,
* preserve public Step versus Node-internal Step distinction:

  * `raft_raw_node_step` = public RawNode.Step validation,
  * `raft_raw_node_step_for_node` = lower-level node/internal `r.Step` path.

Do not attempt to complete all advanced raft features in this phase. Specifically defer or keep skeleton behavior for:

* full ProgressTracker inflights and flow control,
* joint consensus / full ConfChangeV2,
* learners and learner promotion semantics beyond safe basic recognition,
* ReadIndex correctness,
* leadership transfer completion,
* snapshot restore/send pipeline beyond log-level helpers already implemented,
* AsyncStorageWrites full behavior,
* CheckQuorum and PreVote if not already simple to implement safely,
* lease-based reads,
* TraceLogger / TLA build behavior.

If a feature is required for a basic test to compile but not yet semantically implemented, return the documented `RAFT_ERR_NOT_IMPLEMENTED`, drop/no-op only where Go semantics allow, and record it as deferred.

Core scope for this phase:

1. C raft state object

Implement or complete the internal `raft_t` object.

It should include, semantically:

* node id,
* current term,
* vote,
* lead,
* state: follower / candidate / leader / pre-candidate if implemented,
* raft log pointer,
* message queue,
* read states queue if currently skeleton-only,
* election timeout,
* heartbeat timeout,
* randomized election timeout if the repo has randomization support,
* election elapsed,
* heartbeat elapsed,
* votes map or simple vote tracking structure,
* current voters set sufficient for simple majority,
* basic progress map for voters if already present, or minimal internal progress needed for append replication,
* config flags from v3.7.0:

  * CheckQuorum,
  * PreVote,
  * ReadOnlyOption,
  * DisableProposalForwarding,
  * MaxSizePerMsg,
  * MaxUncommittedEntriesSize,
  * MaxInflightMsgs,
  * MaxInflightBytes,
  * MaxCommittedSizePerReady,
  * AsyncStorageWrites,
  * Applied.

Use the repository’s existing type names and layout if already established.

2. Initialization

Implement C equivalent of `newRaft(c *Config)` to the minimum needed for this phase.

Requirements:

* validate config fields according to existing C config validation docs,
* reject `ID == RAFT_NONE`,
* require non-nil storage ops,
* call `Storage.InitialState`,
* initialize `raftLog` from Storage,
* load HardState:

  * term,
  * vote,
  * commit,
* initialize committed/applied state consistently with `Config.Applied`,
* initialize voters from ConfState or bootstrap path,
* initialize progress for known voters if progress tracking exists,
* set initial state to follower,
* set `lead = RAFT_NONE`,
* preserve logger handling policy already chosen:

  * Go wrapper owns Go `Logger`,
  * C core may use no-op/stderr/optional logger ops,
  * do not call Go Panicf/Fatalf directly from C.

3. State transitions

Implement basic equivalents of:

* `becomeFollower(term, lead)`,
* `becomeCandidate()`,
* `becomeLeader()`.

Requirements:

* term and vote updates must follow Go semantics.
* becoming leader must append an empty no-op entry for the new term.
* leader should initialize its own progress as matched to last index.
* follower lead should become `RAFT_NONE` when unknown.
* do not allow invalid state transitions to silently corrupt state.

4. Ticking

Implement:

* `raft_raw_node_tick`,
* `raft_raw_node_tick_quiesced`, if currently skeleton-only, with safe minimal behavior,
* internal election tick,
* internal heartbeat tick.

Basic behavior:

* follower/candidate election tick increments election elapsed and triggers `MsgHup` when timeout elapses.
* leader heartbeat tick sends heartbeats when heartbeat timeout elapses.
* heartbeat messages should use current committed index where appropriate.

If randomized election timeout is not fully implemented, use a deterministic safe value and document the limitation. Prefer matching Go behavior if existing helpers already support randomness.

5. Step handling

Implement minimal internal `raft_step` or equivalent.

Required message handling for this phase:

* `MsgHup`:

  * starts election/campaign,
  * increments term as candidate,
  * votes for self,
  * sends vote requests to voters,
  * becomes leader immediately in single-node quorum.
* `MsgVote`:

  * grants/rejects vote based on term, vote state, and log up-to-date check.
* `MsgVoteResp`:

  * records votes,
  * becomes leader on quorum,
  * becomes follower on quorum rejection if matching Go semantics for this basic path.
* `MsgProp`:

  * leader appends proposed entries to its log,
  * leader broadcasts append to followers,
  * non-leader behavior must follow current design:

    * forward to leader if proposal forwarding is supported and leader known,
    * otherwise return/drop with documented error.
* `MsgApp`:

  * follower checks prev log index/term,
  * appends entries if matching,
  * advances commit up to leader commit,
  * replies with `MsgAppResp`.
* `MsgAppResp`:

  * leader updates minimal follower progress,
  * advances commit when quorum matched,
  * sends more append if needed.
* `MsgHeartbeat`:

  * follower updates leader,
  * advances commit safely,
  * replies with `MsgHeartbeatResp`.
* `MsgHeartbeatResp`:

  * leader may send append if follower is behind; minimal safe behavior is acceptable.
* `MsgBeat`:

  * leader broadcasts heartbeat.
* local/internal messages needed by `ReportUnreachable` / `ReportSnapshot` may remain skeleton unless tests require them.

Preserve `raft_raw_node_step` versus `raft_raw_node_step_for_node` layering:

* `raft_raw_node_step` should perform public RawNode.Step validation and then delegate to `raft_raw_node_step_for_node`.
* `raft_raw_node_step_for_node` should call the internal raft step path directly.
* `raft_raw_node_step_for_node` must not call `raft_raw_node_step`.

Do not bypass `raftLog` invariants.

7. Message queue and Ready integration

Implement or complete C message queue handling.

Requirements:

* raft core appends outgoing messages to a C-owned message queue.
* `raft_raw_node_ready` / `ready_without_accept` should expose messages through `Ready.Messages`.
* `acceptReady` should drain or mark messages consistent with Go semantics.
* messages must be C-owned and deep-copied as needed.
* entry and snapshot payload ownership must follow type-separated payload rules.
* do not retain Go pointers.

`Ready` should now become meaningfully populated for basic tests:

* SoftState changes if SoftState is implemented,
* HardState when term/vote/commit changes,
* Entries from unstable log,
* CommittedEntries from raftLog,
* Messages from outbound queue,
* MustSync computed correctly:

  * entries exist,
  * term changed,
  * vote changed,
  * not commit-only.

8. HardState / SoftState

Implement or complete:

* current HardState extraction,
* SoftState extraction,
* empty-state comparison helpers if not already implemented,
* prevHardState / prevSoftState tracking in RawNode.

Requirements:

* term, vote, commit must be correct.
* `Ready.HardState` should be non-empty when HardState changes.
* `Ready.MustSync` must not compare commit.
* `Ready.SoftState` should report lead and raft state when changed, if SoftState is already part of C Ready.

9. Basic progress / quorum

This phase needs enough progress/quorum behavior to support:

* single-node election and commit,
* simple multi-node vote quorum,
* basic leader append replication and commit.

Do not implement full v3.7.0 `tracker.ProgressTracker` yet if that is scheduled for a later phase, but do not fake quorum unsafely.

Minimum acceptable behavior:

* maintain a voter id list,
* maintain vote granted/rejected state,
* calculate majority as `voter_count/2 + 1`,
* maintain basic `match` and `next` per voter for leader append commit,
* expose `raft_raw_node_has_progress(id)` accurately for known voters,
* make `WithProgress` progress snapshot return meaningful basic progress rows if the C progress map exists.

Document exactly which full tracker features remain deferred:

* inflights,
* probe/replicate/snapshot states,
* learners,
* joint consensus,
* max inflight bytes,
* optimistic pipelining.

10. Proposal behavior

Implement leader proposal append for normal entries.

Requirements:

* reject empty proposal entries only if Go does,
* preserve entry data ownership,
* set entry term/index correctly,
* append to unstable log,
* update own match index,
* attempt commit for single-node quorum immediately,
* broadcast append for multi-node.

If MaxUncommittedEntriesSize is not fully implemented yet, document as deferred or implement the basic check if the log subsystem already has size helpers.

11. Bootstrap integration

If `raft_raw_node_bootstrap` already appends initial config changes and initializes membership, ensure the new raft state machine can use that membership for quorum/progress.

If bootstrap is still skeleton-only, implement only what is needed for:

* single-node bootstrap,
* simple multi-node initial voters,
* committed bootstrap confchange entries visible through Ready if the existing design requires it.

Do not implement full ConfChangeV2 in this phase unless already present.

13. Tests

Add focused C unit tests for the minimal raft core.

Use the repository’s C test framework and Makefile targets.

At minimum, cover:

A. Initialization

* new raft rejects ID 0.
* new raft loads HardState term/vote/commit.
* new raft initializes log from storage.
* new raft starts as follower with no leader.

B. Election

* single-node campaign becomes leader.
* leader appends no-op entry on election.
* multi-node candidate sends `MsgVote`.
* candidate becomes leader after quorum vote responses.
* candidate rejects/steps down on higher term message.

C. Vote handling

* follower grants vote when term is current/new and log is up-to-date.
* follower rejects stale term vote.
* follower rejects candidate with stale log.

D. Proposal

* leader appends proposed entry.
* single-node leader commits proposal.
* follower/non-leader proposal behavior matches documented current policy.

E. AppendEntries

* follower accepts matching append.
* follower rejects append with mismatched prev log term/index.
* follower advances commit to leader commit safely.
* leader handles successful append response and advances commit with quorum.

F. Heartbeat

* leader tick emits heartbeat.
* follower heartbeat response is produced.
* heartbeat updates known leader.

G. Ready

* Ready contains unstable entries after campaign/proposal.
* Ready contains committed entries after commit.
* Ready contains outgoing messages after vote/app/heartbeat.
* Ready.MustSync is true for entries/term/vote changes.
* commit-only Ready does not force MustSync.
* Advance does not require passing Ready back to C.

H. Step layering

* public `raft_raw_node_step` rejects local messages.
* `raft_raw_node_step_for_node` accepts the corresponding internal/local path where appropriate.
* `raft_raw_node_step` delegates to `raft_raw_node_step_for_node`, not the reverse.

I. Progress helper

* `raft_raw_node_has_progress(id)` returns true for known voters.
* returns false for unknown ids.
* does not expose internal progress pointers.
* progress snapshot, if implemented, reports basic match/next/type.

Add Go/cgo tests only if the C-backed path can run them without requiring unimplemented higher-level features. Otherwise keep tests at the C unit level and document cgo limitations.
